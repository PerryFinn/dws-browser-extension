# SWQA Prompt 模板新增/更新双场景设计

## 背景

当前 SWQA popup 只有一套 `Prompt 模板（持久化保存，可编辑占位符）` 和一个 `复制 Prompt` 按钮。

现状问题：

- 默认模板语义只覆盖“新增接口”场景。
- 当接口已存在、仅需跟进 SWQA 变更时，缺少“更新接口”的专用 Prompt。
- popup 中缺少对“新增 / 更新”用途的显式区分，容易误用。
- 当前模板只能在 popup 中编辑，用户希望“更新”的 Prompt 也能像现有“新增”一样持久化，并在 options 页面修改。

本设计只覆盖 SWQA Prompt 模板的交互、默认文案和持久化方案，不包含具体实现代码。

## 目标

- 支持 `新增` 和 `更新` 两套独立 Prompt 模板，并分别持久化。
- popup 中通过一个 `用途` 字段在 `更新 / 新增` 之间切换，默认使用 `更新`。
- popup 中只保留一个复制按钮，但复制行为和文案跟随当前用途变化。
- options 页面支持编辑两套模板，并与 popup 共享同一份持久化数据。
- “更新”场景下的默认 Prompt 必须先搜索现有实现、先列出差异、等待用户确认后再修改；若未找到实现，再询问是否按新增接口处理。

## 非目标

- 不新增自动抓取本地现有接口实现代码的能力。
- 不修改现有占位符集合。
- 不引入额外的 SWQA 独立设置页面。
- 不在本次设计中扩展更多与 Prompt 生成无关的 SWQA 配置项。

## 方案选择

本次确认采用以下方案：

- popup 中增加一个 `用途` 横向单选字段。
- 用途选项只有 `更新` 和 `新增` 两项。
- 默认选中 `更新`。
- 当前页面只显示当前用途对应的模板内容。
- 页面只保留一个复制按钮，按钮文案跟随用途变化。
- 上述“只保留一个复制按钮”仅指 Prompt 复制按钮；现有 JSON 复制按钮不在本次改动范围内。

备选但未采用的方案：

- 使用两个复制按钮并列展示：被放弃，因为最终希望操作面只保留一个按钮。
- 使用 Select 下拉展示用途：被放弃，因为用途只有两个值，横向单选更直接。
- 拆出独立 SWQA 设置页面：被放弃，因为当前配置量较小，挂在现有设置页即可。

## Popup 交互设计

### 用途字段

- 字段名：`用途`
- 展示形式：横向单选
- 值：
  - `更新`
  - `新增`
- 默认值：`更新`
- 用途切换只影响当前页面显示和复制行为，且用途本身不持久化。

不持久化 `用途` 的原因：

- 用户已明确要求默认使用 `更新`。
- 若持久化上次选择，下一次打开 popup 可能停留在 `新增`，与默认行为冲突。

### 模板输入区

- 字段名保留为：`Prompt 模板（持久化保存，可编辑占位符）`
- 输入区只展示当前用途对应的模板内容。
- 当用途切换时，输入区切换为另一套模板。
- 修改输入区内容时，直接写入当前用途对应的持久化模板。

### 复制按钮

- 页面只保留一个 Prompt 复制按钮。
- 按钮文案根据用途变化：
  - 用途为 `更新` 时：`复制更新 Prompt`
  - 用途为 `新增` 时：`复制新增 Prompt`
- 点击按钮时，基于当前用途对应模板和当前提取到的接口信息生成 Prompt 并复制。
- 现有 `复制 JSON` 按钮保持不变，不受本次设计影响。

### Tooltip 文案

- `用途` tooltip：
  `选择当前正在编辑和复制的 Prompt 模板。默认使用“更新”，切换后输入区会显示对应模板内容。`

- `复制更新 Prompt` tooltip：
  `基于当前“更新”模板和已提取的接口信息生成 Prompt 并复制。默认更新模板会引导模型先搜索现有实现、先列出差异、待你确认后再修改；如果你已自定义模板，则以当前模板内容为准。`

- `复制新增 Prompt` tooltip：
  `基于当前“新增”模板和已提取的接口信息生成 Prompt 并复制，用于新增一个接口实现。`

## Options 页面设计

本次确认将配置入口放在现有设置页中，而不是新增 SWQA 独立设置页。

设置页在现有 `/settings/base` 页面中增加一个 `SWQA Prompt 模板` 分组，交互与 popup 保持一致：

- 有一个 `用途` 横向单选，默认选中 `更新`
- 有一个 `Prompt 模板（持久化保存，可编辑占位符）` 输入区
- 输入区展示当前用途对应模板
- 修改内容时直接写入对应 storage

这样可以保证：

- popup 与 options 的操作心智一致
- 用户可以在 popup 里快速临时调整
- 用户也可以在 options 页面里更舒适地编辑长模板

## 持久化设计

两套模板使用两份独立 storage key：

- `swqaCreatePromptTemplate`
- `swqaUpdatePromptTemplate`

采用独立 key 的原因：

- 结构简单，便于在 popup 和 options 中直接读写
- 与现有单值存储方式一致
- 避免额外引入一个对象结构及其迁移逻辑

默认值应纳入统一的本地存储默认值管理，确保：

- 新安装用户可直接获得两套默认模板
- 重置本地配置时两套模板都能恢复默认值

### 旧数据迁移规则

当前线上已有单 key：

- `swqaPromptTemplate`

### 初始化、迁移顺序与执行契约

由于当前仓库已存在统一默认值初始化逻辑，本次需求必须额外定义 SWQA Prompt 模板的初始化顺序，避免升级用户的旧模板在默认值初始化阶段被覆盖。

要求如下：

- SWQA Prompt 模板的迁移与初始化必须先于新 key 的默认值写入执行。
- 不允许先把 `swqaCreatePromptTemplate` / `swqaUpdatePromptTemplate` 用默认值初始化，再依赖“首次读取时迁移”；否则旧 `swqaPromptTemplate` 将失去迁移触发条件。
- SWQA Prompt 模板的迁移执行入口由 background 侧统一负责，popup 与 options 不各自实现迁移逻辑。
- background 必须在以下时机触发迁移感知初始化：
  - `chrome.runtime.onStartup`
  - `chrome.runtime.onInstalled` 的 `install`
  - `chrome.runtime.onInstalled` 的 `update`
- popup 与 options 可以直接读取 storage，但在迁移尚未完成前不得仅因首次渲染拿到默认值就把默认模板回写到 storage。
- 对升级用户的最低保证是：扩展完成 `update` 初始化后，首次重新打开 popup 或 options 时，应能读到迁移后的模板值，而不是被新默认值覆盖。
- 实现上可采用任一方式，只要满足上述顺序约束：
  - 在统一初始化流程中，为 SWQA Prompt 模板增加迁移感知逻辑。
  - 或将 SWQA Prompt 模板从通用默认值初始化中单独剥离，走专门的迁移初始化流程。

迁移规则定义如下：

- 新逻辑只读取 `swqaCreatePromptTemplate` 和 `swqaUpdatePromptTemplate`；旧 `swqaPromptTemplate` 仅用于迁移输入，不再作为运行时读取源。
- 迁移时按“新 key 优先、旧 key 只补 create、不覆盖已有新 key”的原则处理。
- `swqaUpdatePromptTemplate` 不从旧 key 推导，缺失时始终使用“更新模板默认值”初始化。
- 旧 key 在本次需求中不要求立即清理；可保留但忽略，避免额外引入删除失败或回滚兼容问题。

### storage 状态优先级表

| create key | update key | old key | 结果 |
|------------|------------|---------|------|
| 存在 | 存在 | 任意 | 直接使用 create/update 现值，不再参考 old key |
| 存在 | 不存在 | 存在或不存在 | 保留 create 现值；update 用更新模板默认值初始化 |
| 不存在 | 存在 | 存在 | create 由 old key 迁入；保留 update 现值 |
| 不存在 | 存在 | 不存在 | create 用新增模板默认值初始化；保留 update 现值 |
| 不存在 | 不存在 | 存在 | create 由 old key 迁入；update 用更新模板默认值初始化 |
| 不存在 | 不存在 | 不存在 | create 用新增模板默认值初始化；update 用更新模板默认值初始化 |

说明：

- “存在”仅表示 key 已存在；其值无论是普通字符串、空字符串还是仅空白字符串，都视为用户已保存的值，不参与迁移覆盖。
- 旧 key 只用于补 create，不用于补 update。
- 任一新 key 一旦存在，就以该 key 自身值为准，不再被旧 key 覆盖。

该策略的原因：

- 旧模板语义是“新增接口”，映射到 `swqaCreatePromptTemplate` 最符合用户已有认知。
- 更新模板是本次新增出来的独立场景，需要专用默认值，不能直接复用旧模板。
- 暂不强制清理旧 key，可以把迁移范围收敛在“读新 key、兼容旧数据”。

## 占位符策略

现有可用占位符保持不变：

- `{{json}}`
- `{{url}}`
- `{{interfaceId}}`

本次默认模板文案中不额外插入 `接口文档地址` 和 `interfaceId` 行。

说明：

- 用户已明确要求默认模板保持简洁，不主动额外输出这两行。
- 仍保留这两个占位符能力，用户可在后续自行编辑模板时按需加入。

### 新增模板默认值

````text
向 `src/services/models` 添加一个新的接口请求，以下是该接口的描述信息：
```json
{{json}}
```

请遵循项目现有的接口封装、命名和类型定义方式进行处理。
如果信息不足以支持实现，请先指出缺失项，不要自行猜测。
输出时请说明需要新增或修改哪些文件。
````

### 更新模板默认值

````text
你需要更新 `src/services/models` 中一个已有接口请求实现，以下是该接口最新的描述信息：
```json
{{json}}
```

请严格按以下流程执行：

1. 先不要直接修改代码。
2. 先根据接口路径、请求方法、名称和字段信息，在代码库中搜索对应的现有接口实现及相关类型定义。
3. 如果找到候选实现，先输出一份“差异清单”，至少包含：
   - 请求路径或请求方法是否变化
   - 请求参数是否变化
   - 响应结构或字段是否变化
   - 字段的新增、删除、重命名或类型变化
   - 兼容性风险
   - 可能受影响的文件
4. 差异清单输出后，等待我确认；在我明确确认之前，不要直接给出修改后的代码。
5. 如果我确认需要修改，再根据确认后的范围给出具体改动方案或代码。
6. 如果没有找到对应实现，不要直接新增；先明确说明“未找到对应实现”，再询问我是否要按新增接口处理。
7. 如果对比后没有实质差异，请明确说明“无需修改”以及原因。
8. 如果接口文档信息不足，请明确指出缺失项，不要猜测。
````

## 数据流与行为约束

- popup 从当前用途对应的模板 storage 中读取模板内容。
- options 页面从同一份 storage 中读取模板内容。
- 用户在任一入口修改模板后，数据源以 storage 中的最新持久化值为准。
- 本次需求不强制要求 popup 与 options 在两个已打开页面之间做实时联动刷新。
- 本次需求要求的最低一致性是：任一入口在重新打开、重新挂载，或收到 storage 变更传播后，应读取到最新持久化值。
- 复制动作只基于当前用途对应模板生成 Prompt。
- 当前接口未提取成功时，复制按钮保持禁用。

## 错误处理与边界情况

- 输入区始终展示当前 storage 中的原始值，不在渲染阶段自动回填默认模板。
- 如果当前用途模板值为空字符串或仅包含空白字符，复制动作回退到对应用途的默认模板。
- 当复制动作因空模板回退到默认模板时，不自动写回 storage。
- 如果用户把模板编辑为不含任何占位符，仍允许保存；系统只负责按模板原样生成。
- 如果当前页面提取不到接口信息，则复制动作不可用。
- 如果用户在 options 页面修改模板，popup 下次打开时应直接读取最新模板。
- 如果未来需要为“更新”场景提供更强的比对能力，例如注入现有实现代码，应作为独立需求处理，不混入本次设计。

## 验收标准

- popup 中可在 `更新 / 新增` 间切换，默认是 `更新`。
- popup 中只有一个 Prompt 复制按钮，按钮文案随用途变化。
- popup 中现有 `复制 JSON` 按钮保持不变。
- popup 中 `更新` 和 `新增` 使用两套独立模板。
- options 页面可编辑这两套模板。
- popup 与 options 编辑同一份持久化数据。
- 升级用户的旧 `swqaPromptTemplate` 会按迁移规则补入 `swqaCreatePromptTemplate`，且不会被新默认值覆盖。
- 新增默认模板不额外输出 `接口文档地址` 与 `interfaceId`。
- 更新默认模板满足“先搜索实现 -> 先列差异 -> 用户确认 -> 再修改 -> 找不到则询问是否按新增处理”的流程约束。
- Tooltip 仅描述默认模板的推荐行为，不对用户自定义模板增加系统级强制约束。
