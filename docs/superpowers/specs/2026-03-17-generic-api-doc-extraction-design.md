# 通用 API 文档提取设计

## 背景

当前扩展中的接口提取能力是为 `swqa.gz.cvte.cn/interface/:id` 定制的：

- popup 只识别 SWQA 接口详情页。
- 命中页面后，通过 background 注入脚本，在页面 `MAIN` world 内借当前登录态调用 SWQA 同源接口详情 API。
- 拿到响应后，经过一套 SWQA 专用清洗逻辑，生成精简 JSON，并可基于模板复制 Prompt。

这条链路的优点是确定性高、输出稳定，但它本质上不是“通用 API 文档提取器”，而是“SWQA 站点专用提取器”。

本次设计要解决的问题是：在不影响现有 SWQA 功能的前提下，为其它 API 文档页面新增一条通用提取能力。由于不同文档站点页面结构差异很大，通用路径需要引入大模型参与结构化抽取。

## 目标

- 保留现有 SWQA 专用提取链路，不回退已有能力。
- 新增 `通用 API 文档提取` 能力，面向任意域名的单接口文档页面。
- 通用提取采用 `用户辅助定位 + 模型结构化抽取` 的模式，而不是全自动识别。
- 通用提取的 `v1` 输出一份标准档统一 JSON，并同时生成可复制的 Prompt。
- popup 结果页同时展示：
  - 统一 JSON
  - Prompt 预览
  - 不确定项列表
- 通用提取的模型请求由用户在 options 中配置，插件负责编排调用，不绑定单一模型供应商。

## 非目标

- 不替换现有 SWQA 专用提取逻辑。
- 不在 `v1` 支持批量接口提取或整页提取。
- 不追求“打开任意 API 文档页后零操作自动识别接口区域”。
- 不在 `v1` 建立多站点专用适配器体系。
- 不在 `v1` 做 provider marketplace、供应商模板市场或复杂的模型路由策略。
- 不在 `v1` 自动修改业务代码；最终动作仍然是复制 Prompt 交给外部模型或人工继续操作。

## 方案选择

### 采用方案

本次确认采用以下产品形态：

- `SWQA 专用提取` 与 `通用 API 文档提取` 并存。
- 命中 SWQA 页面时，默认继续走现有 SWQA 快路径。
- 其它页面走通用提取路径。
- SWQA 页面额外提供一个次级入口，允许用户改走通用提取，但不抢主流程。

### 备选但未采用的方案

- 把 SWQA 也并入新通用链路：
  被放弃，因为会主动放弃当前最稳定的一条能力，并显著增加回归风险。
- 所有页面都直接走模型直抽：
  被放弃，因为结果稳定性过度依赖模型，且不利于调试和追责。
- 优先做常见文档系统适配器：
  被放弃，因为这与“任意域名”目标不一致，且会把首版范围转成站点兼容性工程。

## 产品边界

### v1 覆盖范围

- 一次只处理 `单个接口`。
- 用户辅助定位方式为：
  - `DOM 点选优先`
  - `当前文本选区兜底`
- 主用途为：
  - 生成统一 JSON
  - 进一步生成可复制的 Prompt，交给其它大模型继续完成代码生成或代码更新工作
- 通用路径采用“平衡模式”：
  - 尽量产出结果
  - 但明确标记不确定项
  - 不静默猜测

### 成功标准

对通用提取来说，`v1` 的成功不是“完全理解所有文档站点”，而是：

- 在任意域名下，用户能明确指定一个接口文档区域。
- 插件能把这个区域转成一份结构稳定、可核对、可复用的统一 JSON。
- 当存在信息缺失或歧义时，结果中明确保留不确定项，并在 Prompt 中引导下游模型先向用户确认，再继续执行。

## 核心用户流程

### SWQA 页面

- popup 打开后，若当前页面命中 `swqa.gz.cvte.cn/interface/:id`：
  - 默认进入现有 `SWQA 接口提取` 视图。
  - 继续使用现有 SWQA 专用提取链路。
  - 现有“提取并清洗 / 复制 JSON / 复制 Prompt”行为保持不变。
  - 额外提供一个不抢主流程的次级入口：`改用通用提取`。

### 非 SWQA 页面

- popup 打开后进入 `通用 API 文档提取` 视图。
- 首先检查通用提取模型配置是否可用。
- 若配置不可用：
  - 阻止开始提取。
  - 给出明确错误提示。
  - 提供跳转到 options 的入口。
- 若配置可用：
  - 提供两个动作：
    - `开始点选区域`
    - `使用当前选中文本`
- 用户完成采集后：
  - popup 展示本次采集摘要，例如页面标题、URL、片段预览。
  - 用户再执行 `提取并生成`。
- 提取完成后进入结果页，同时展示：
  - 统一 JSON
  - Prompt 预览
  - 不确定项列表
  - `复制 JSON`
  - `复制 Prompt`
  - `重新点选 / 重新读取选区 / 重新提取`

### 失败重试

- 如果模型调用失败或结构化失败，不清空已采集内容。
- 用户可直接重试模型调用，而不必重新点选。
- 只有在采集内容本身不对时，才需要重新采集。

## 架构设计

本次需求不把通用提取逻辑塞进现有 SWQA 文件内部，而是在现有功能旁边新增一条独立链路。

推荐的整体结构如下：

- `Popup UI 层`
  - SWQA 专用卡片
  - 通用提取卡片
  - 结果展示区
- `提取编排层`
  - 页面识别器
  - SWQA extractor
  - Generic extractor
  - Prompt 生成器
- `基础能力层`
  - 页面点选覆盖层
  - 文本选区读取
  - 模型 Provider 调用
  - JSON Schema 校验
  - 配置存储

### 设计原则

- SWQA 与 Generic 在产品上并存，在实现上分离。
- 两条路径可以共享：
  - 结果展示区
  - 复制能力
  - 部分 storage 基础设施
- 但两条路径不共享核心提取逻辑。

这样做的原因是：

- SWQA 是“接口直拉 + 清洗”，属于确定性提取。
- Generic 是“用户辅助采集 + 模型抽取 + 校验”，属于非确定性提取。
- 两者的错误模型、调试方式、演进节奏都不同，不应混在一个提取器内部。

## 模块划分

### 1. Popup / Options 层

#### Popup

- 负责根据当前页面状态展示：
  - SWQA 专用视图
  - 通用提取视图
  - 结果视图
- 负责展示：
  - 当前采集状态
  - 错误提示
  - JSON / Prompt / 不确定项
- 不在 popup 内实现站点级提取逻辑或 provider 细节。

#### Options

- 新增一组 `通用提取模型配置`。
- 新增一组 `通用提取 Prompt 模板配置`。
- 负责承载配置编辑、测试连接和基础说明文案。

### 2. Capture 层

位于内容脚本侧，负责把页面上的“用户意图区域”转成可送给模型的原始上下文。

包括两类能力：

- `DOM 点选`
  - 在页面上激活覆盖层
  - 用户点击一个接口详情区域
  - 读取该区域对应 DOM 片段
- `文本选区`
  - 读取用户当前选中的文本
  - 用于兜底处理结构怪异或难以点选的页面

Capture 层只负责采集，不负责解释为接口结构。

### 3. 提取编排层

负责统一管理提取入口与状态流转。

主要职责：

- 识别当前页面是否命中 SWQA 快路径。
- 对 SWQA 页面路由到现有 SWQA extractor。
- 对其它页面路由到 Generic extractor。
- 统一输出结果态：
  - JSON
  - Prompt
  - uncertainties
  - error

### 4. Provider 层

Provider 层只服务 Generic extractor，用于把采集到的原始上下文发送到用户配置的模型端点。

`v1` 选型如下：

- 采用 `ai` 生态作为统一抽象层。
- 默认 provider 类型：
  - `OpenAI Compatible`
  - `OpenAI`
- 推荐依赖：
  - `ai`
  - `@ai-sdk/openai-compatible`
  - 视 OpenAI 官方专用能力需要，再引入 `@ai-sdk/openai`
- `v1` 不额外引入官方 `openai` SDK，避免在 provider 层并存两套调用抽象。

采用该方案的原因：

- 目标是让用户配置 `base URL / model / key` 后，插件能统一编排调用。
- `OpenAI Compatible` 足以覆盖绝大多数兼容 OpenAI 协议的模型服务。
- `ai` 生态已经对 provider 差异做了较好的统一封装，适合扩展场景。

## 配置设计

### 通用提取模型配置

options 中新增如下配置项：

- `API 类型`
  - `OpenAI Compatible`
  - `OpenAI`
- `Base URL`
- `Model ID`
- `API Key`
- `测试连接`

### 配置行为约束

- 未完成配置时，通用提取不可开始。
- `测试连接` 只验证：
  - 配置是否可发起请求
  - 目标模型是否能返回结构化结果
- `测试连接` 不负责验证提取质量。

### Prompt 模板配置

通用提取在 `v1` 使用一套独立的 generic prompt 模板配置，不复用现有 SWQA 的 create/update 模板 storage。

这样做的原因：

- 保证现有 SWQA 配置和行为完全不受影响。
- 通用提取与 SWQA 的输入来源不同，不应强绑在同一组配置上。
- `v1` 先收敛为一套 generic 模板，降低配置复杂度。

### 占位符策略

generic prompt 模板支持以下最小占位符：

- `{{json}}`
- `{{url}}`

`v1` 不为 Generic 路径引入额外的 `{{uncertainties}}` 占位符。

当结果中存在不确定项时，由 Prompt 生成器在模板结果后自动追加一段标准引导语，而不是要求用户手动维护额外占位符。

## Generic 提取数据流

### 采集阶段

Generic 路径的输入不是“整个页面 HTML”，而是用户明确圈定的采集上下文。

采集产物至少包括：

- 当前页面 URL
- 当前页面标题
- 采集模式：
  - `generic-dom`
  - `generic-selection`
- 原始文本片段
- 原始 DOM 片段摘要（若来自点选）

### 预处理阶段

在送给模型前，先做轻量预处理：

- 清理明显无关的 UI 文本噪声。
- 保留标题、路径、参数表、示例、响应区块等高价值片段。
- 形成一份统一的“抽取上下文”。

预处理的目标不是替代模型，而是：

- 降低噪声
- 控制 token 成本
- 提高结构化稳定性

### 模型抽取阶段

Generic extractor 将抽取上下文发送给 Provider 层，并要求模型返回统一 JSON。

模型输出必须经过本地校验，不允许把任意自然语言结果直接视为成功。

### 校验与回收阶段

模型输出先经过 schema 校验，再做基础语义校验。

只有在校验通过后，才进入结果展示和 Prompt 生成。

若为部分通过，则允许保留部分结果，但必须输出 `uncertainties`。

## 统一 JSON 设计

`v1` 的统一 JSON 围绕“生成后续代码 Prompt”来设计，不追求大而全，只保留最核心且可稳定抽取的结构。

### 顶层结构

- `source`
- `endpoint`
- `request`
- `response`
- `uncertainties`

### 字段语义

#### `source`

用于描述本次结果来自哪里，便于 Prompt 引用与后续排查。

建议包含：

- `url`
- `title`
- `mode`

#### `endpoint`

用于描述接口本身。

建议包含：

- `name`
- `path`
- `method`
- `description`

#### `request`

用于描述请求侧结构。

建议包含：

- `pathParams`
- `queryParams`
- `headers`
- `body`
- `auth`

其中：

- `headers` 和 `auth` 可为空
- `body` 允许为对象、数组、标量说明或 `null`

#### `response`

用于描述响应侧结构。

建议包含：

- `successBody`
- `errorNotes`

其中 `errorNotes` 可为空。

#### `uncertainties`

用于表达“不确定了什么，以及为什么不确定”。

`v1` 中每项只保留两个字段：

- `field`
- `reason`

示例：

```json
{
  "field": "request.body.userId.type",
  "reason": "文档中只出现字段名与示例值，未明确字段类型"
}
```

### 示例

```json
{
  "source": {
    "url": "https://example.com/api-docs/user-detail",
    "title": "用户详情接口",
    "mode": "generic-dom"
  },
  "endpoint": {
    "name": "获取用户详情",
    "path": "/api/users/{id}",
    "method": "GET",
    "description": "根据用户 ID 获取用户详情"
  },
  "request": {
    "pathParams": [
      {
        "name": "id",
        "type": "string",
        "required": true,
        "description": "用户 ID"
      }
    ],
    "queryParams": [],
    "headers": [],
    "body": null,
    "auth": "Bearer Token"
  },
  "response": {
    "successBody": {
      "id": "string",
      "name": "string",
      "status": "number"
    },
    "errorNotes": null
  },
  "uncertainties": [
    {
      "field": "response.successBody.status",
      "reason": "文档示例中返回数值，但字段说明未明确类型"
    }
  ]
}
```

## Prompt 生成设计

通用提取的结果页需要同时展示统一 JSON 与 Prompt 预览，但主操作仍然是复制 Prompt。

### Prompt 生成规则

- 以 generic prompt 模板为基础。
- 使用统一 JSON 填充 `{{json}}`。
- 使用当前页面 URL 填充 `{{url}}`。
- 当 `uncertainties` 为空时：
  - 直接输出常规 Prompt。
- 当 `uncertainties` 非空时：
  - 在模板结果后自动追加一段标准引导语。

### 不确定项附加引导语

当存在不确定项时，附加引导语必须明确要求下游模型：

- 先列出当前不确定项。
- 先向用户逐项确认。
- 在用户确认前，不要对相关字段做主观假设。
- 若这些不确定项会影响最终代码实现，先暂停生成最终代码。

这样可以保证：

- 统一 JSON 只负责表达事实。
- Prompt 负责把这些事实转成后续交互动作。

## 错误处理

### 1. 配置错误

包括：

- API Key 缺失
- Base URL 非法
- Model ID 缺失
- 测试连接失败

处理方式：

- 禁止开始通用提取。
- 在 popup 中显示明确错误提示。
- 提供跳转到 options 的入口。

### 2. 采集错误

包括：

- 用户未选中任何文本
- 点选区域为空
- 读取到的上下文长度过短

处理方式：

- 不发起模型调用。
- 提示用户重新点选或重新选择文本。

### 3. 模型调用错误

包括：

- 超时
- 401 / 403
- 429
- 5xx
- 网络错误
- 返回体不兼容

处理方式：

- 保留已采集内容。
- 显示错误提示。
- 允许直接重试模型调用。

### 4. 结构化失败

包括：

- 模型返回非 JSON
- 结构缺失严重
- 字段类型不满足 schema

处理方式：

- 尽量输出可保留的部分结果。
- 不能静默视为成功。
- 如可保留，则必须输出 `uncertainties`。
- 如无法保留，则提示重新提取或调整采集范围。

## 安全与隐私边界

由于通用提取会把页面片段发送到用户配置的模型端点，必须明确其安全边界。

要求如下：

- `API Key` 仅保存在本地扩展存储中，不使用 sync 存储。
- popup 主界面不明文展示完整 key。
- 不自动上传调试日志。
- 错误日志中不得打印完整 key 或完整请求头。
- 在通用提取入口附近明确提示：
  - 选中的页面内容会被发送到你配置的模型端点。

## 与现有 SWQA 功能的关系

### 保持不变

- SWQA 页面识别规则不变。
- SWQA 同源接口拉取逻辑不变。
- SWQA 清洗逻辑不变。
- 现有 SWQA Prompt 模板能力不变。

### 新增但不影响原能力

- 在 SWQA 页面增加次级入口：`改用通用提取`。
- 在非 SWQA 页面增加通用提取视图。
- 在 options 中增加 generic 提取配置。

### 约束

本次需求不得通过“把 SWQA 逻辑重写为 Generic 的一个分支”来实现，以避免引入不必要的结构性回归。

## 验证与验收标准

### 最低验收标准

1. 在 SWQA 页面，原有提取和 Prompt 复制功能不回归。
2. 在非 SWQA 页面，用户可以通过：
   - 点选区域
   - 当前文本选区
   两种方式进入通用提取。
3. 模型配置正确时，插件可以在 popup 内完成一次通用提取并生成统一 JSON。
4. 结果页同时展示：
   - 统一 JSON
   - Prompt 预览
   - 不确定项列表
5. 当存在不确定项时，复制出来的 Prompt 必须明确要求下游模型先向用户确认，而不是直接猜测。
6. 模型调用失败时，已采集内容不会丢失，用户可以直接重试。
7. 配置缺失或无效时，用户得到明确引导，而不是模糊报错。
8. `v1` 默认只支持单接口提取，不支持批量。

### 实施后的验证建议

- 运行 `pnpm verify`。
- 手动验证以下路径：
  - SWQA 页面原链路
  - 非 SWQA 页面点选提取
  - 非 SWQA 页面文本选区提取
  - 模型配置缺失
  - 模型配置无效
  - 模型调用失败后直接重试
  - 结果中存在不确定项时的 Prompt 文案

## 演进方向

以下内容明确留到后续版本，不纳入 `v1`：

- 常见 API 文档系统专用适配器
- 批量接口提取
- 更复杂的 provider 预设
- Generic 路径多模板或用途细分
- 更精细的语义校验与字段置信度评分

`v1` 的目标是先把：

- 用户辅助采集
- 模型结构化抽取
- schema 校验
- uncertainties 驱动的 Prompt 生成

这条核心闭环跑通。
